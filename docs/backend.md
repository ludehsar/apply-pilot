# Backend — `apps/api` (Axum · Diesel · utoipa)

## Layout

```
apps/api/
  diesel.toml                     Diesel CLI config (schema output: src/schema.rs)
  migrations/<version>_<name>/    up.sql / down.sql, embedded and run on boot
  src/
    main.rs       bootstrap: config → pool + migrations → router under /api/v1 → Swagger
    config.rs     all env access
    db.rs         Pool type, connect(), embedded migrations
    error.rs      AppError → JSON 500, AppResult<T>
    schema.rs     generated by Diesel (never edit by hand); appears with the first table
    routes/
      mod.rs      router(): one `.routes(routes!(...))` per endpoint group
      health.rs   GET /api/v1/health
```

## Routing and the `/api/v1` prefix

`main.rs` nests `routes::router()` under `/api/v1` **once**. Route modules declare paths relative to it:

```rust
#[utoipa::path(get, path = "/users/{id}", tag = "users", responses((status = 200, body = User)))]
pub async fn get_user(...) -> AppResult<Json<User>> { ... }
```
This serves `GET /api/v1/users/{id}` and shows up in the docs under that full path.

Register handlers in `routes/mod.rs`:

```rust
OpenApiRouter::new()
    .routes(routes!(health::health))
    .routes(routes!(users::list_users, users::create_user))
```
`routes!()` groups handlers that share a path (e.g. GET and POST on `/users`). Handlers on a different path need their own `.routes(...)` call.

## API documentation (OpenAPI + Swagger UI)

- `utoipa` generates the OpenAPI spec from `#[utoipa::path]` attributes and `#[derive(ToSchema)]` types; `utoipa-axum` collects them as routes are registered.
- Swagger UI: **http://localhost:8080/docs**. Raw spec: **/openapi.json**.
- Every handler **must** have `#[utoipa::path]`, and every request/response type **must** derive `ToSchema`. Undocumented routes don't count as done.
- The Swagger UI assets are vendored (`vendored` feature), so builds need no network.

## Database (Diesel)

- `diesel-async` with a `bb8` pool (`db::Pool`) talks to Postgres in pure Rust (tokio-postgres), so there's no libpq at runtime.
- Get a connection in a handler with `let mut conn = pool.get().await?;`, then use `diesel_async::RunQueryDsl` methods (`.load`, `.get_result`, `.execute`) with `.await`.
- Migrations: create them with the CLI, then apply locally (that also regenerates `src/schema.rs`):

  ```bash
  cd apps/api
  diesel migration generate create_users
  diesel migration run          # applies + rewrites src/schema.rs
  diesel migration redo         # test down.sql
  ```
  The API also runs pending migrations on boot (`embed_migrations!` in `db.rs`), so deployed environments migrate themselves.
- On the first table, add `mod schema;` to `main.rs`.
- Tables with `updated_at` call `SELECT diesel_manage_updated_at('<table>');` in their migration. The helper comes from the initial Diesel migration.
- Never edit a migration that has already run in a shared environment; add a new one.
- Install the CLI if it's missing: `cargo install diesel_cli --no-default-features --features postgres`.

## Errors

- Handlers return `AppResult<T>`. `?` converts Diesel and pool errors into `AppError`, which logs the error and returns `500 {"error":"internal_error"}`.
- When an endpoint needs another status (404, 422, …), add a variant to `AppError` with its status in `into_response`. Don't build ad-hoc `(StatusCode, Json)` tuples in handlers.
